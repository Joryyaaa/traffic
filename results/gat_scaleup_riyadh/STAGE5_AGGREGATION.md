# Stage 5: cross-size aggregation and results layout

`scripts/aggregate_gat_scaleup.py` merges the three screening arrays' per-seed
results into one comparison table: segment count | mean return | std | success
rate | train time/seed. Same per-task CSV layout `scripts/aggregate_sweep.py`
already reads (`<root>/task_<seed>/results.csv`); this script adds the cross-size
table on top rather than duplicating that reader.

## The critical instruction this script enforces in code, not just in a doc

> Important: do NOT reuse the fixed 0.6863 benchmark blindly on larger networks.
> Compute zone_builder independently for each network using the same methodology.

`ZONE_BUILDER_BY_SEGMENTS` in the script hardcodes each network's own,
independently-measured benchmark, keyed by segment count, sourced from Stage 2:

| segments | zone_builder | source |
|---|---|---|
| 89 (r400 reference) | 0.6863 | `results/combined_gat_credit_long/` lineage |
| 176 (r445) | 0.8111 | Stage 2, max_closures=10/ep_len=25 |
| 290 (r630) | 0.6115 | Stage 2, max_closures=8/ep_len=20 (corrected from a negative first candidate) |
| 599 (r850) | 0.4636 | Stage 2, max_closures=14/ep_len=35 |

If a size without a recorded benchmark is passed, the script refuses to run
rather than guess or silently fall back to another network's number.

Smoke-tested (not against real Ibex results, which don't exist yet from this
session): ran with a hand-written fake `task_1/results.csv` for the 176-segment
root, confirmed the printed row used **0.8111**, not 0.6863, and the merged CSV
and success-count arithmetic were correct. Cleaned up before committing.

## Usage (once the Stage 4 arrays have produced results)

```bash
python scripts/aggregate_gat_scaleup.py \
    --roots runs/gat_scaleup_r445_5seed:176 \
            runs/gat_scaleup_r630_5seed:290 \
            runs/gat_scaleup_r850_5seed:599 \
    --expect 1-5
```

Add `runs/r400_gat_mzs1_167k:89` to the `--roots` list to include the r400
reference (30-seed COMBINED results, already complete) in the same table for a
full 4-point comparison, once the screening arrays are done.

## Output

`results/gat_scaleup_riyadh/scaleup_comparison.csv` -- one row per size, columns
`segments, n, mean, std, min, max, benchmark, benchmark_source, success,
train_min_mean`. Regenerated by re-running the script; not committed here since
no real run exists yet.

## What this table will need to show, and how to read it

The scientific question (from the mentor's original request, extended by this
scale-up): does the min_zone_size=1 + longer-training combination that worked at
89 segments (mean +0.8365, 29/30 seeds >= its own zone_builder) hold up as the
network grows to ~150/300/600 segments? Two honest readings to watch for once
real data lands:

- **Mean return relative to that size's own benchmark** is the fair comparison
  -- a mean of, say, +0.3 at 599 segments is a *stronger* result relative to its
  +0.4636 benchmark than the same +0.3 would be relative to r400's +0.6863.
- **Success rate, not just mean**, matters given this lineage's own finding
  (GAT-LONG at 167k, mzs=4: mean +0.1618 hid a highly bimodal 1/5 success rate).
  5 screening seeds are too few to trust a success-rate number on their own --
  this table is a go/no-go signal for committing to the full 30-seed run per
  size, not a final result.
